# Phase 13 Context: SEO Analytics Dashboard

## Scope

Phase 13 builds an SEO analytics dashboard at `/admin/settings/seo/analytics` as a single scrollable page with 3 sections:
- **Analytics Overview** — Indexed pages card with trend, top performing pages table with traffic metrics, overview chart
- **Keyword & CTR Analytics** — Keyword rankings table with position and trend indicators, CTR/impressions trend charts with date range selector
- **Health Reports** — 404 errors table with local DB logging, sitemap health via local XML analysis, crawl issues panel with status badges

**Requirements covered:** ANLT-01 through ANLT-07 (7 requirements)

## Decisions

### D-01: Data Source — Honest placeholders for Search Console data

Keyword rankings (ANLT-03), CTR/impressions (ANLT-04), and crawl issues (ANLT-06 partial) use honest placeholder cards with "--" values and notes like "Connect Google Search Console API for real keyword data." This follows the Phase 12 CWV placeholder precedent (D-06/D-07).

GA4 data that's already available (top pages, pageviews, sessions, active users) stays real via the existing `getGa4Summary()` function.

**Why:** Google Search Console API is explicitly deferred to v4 (ANLT-08 through ANLT-10). Faking data or using mock values would mislead admin users. Honest placeholders show the UI is ready and provide a clear activation path.

### D-02: 404 Error Tracking — DB table + proxy.ts logging

Create a `seo_404_errors` table with columns: id, url, referrer, hit_count, last_seen_at, created_at. When proxy.ts encounters a request that matches no route (and no redirect), insert or increment the hit count for that URL. Admin sees a searchable table with URL, referrer source, hit count, and last seen date.

**Why:** Local 404 logging provides real data without any external API dependency. proxy.ts is the project's routing layer (per AGENTS.md) — it's the natural place to detect unmatched routes. Hit counting and deduplication by URL keeps the table manageable.

### D-03: Sitemap Health — Local XML analysis

Read the generated sitemap.xml (or sitemap generation config), count total URLs, check last modified dates, verify XML structure is valid. Show results as status cards: Total URLs, Last Generated, XML Valid (yes/no). No external API needed.

**Why:** The sitemap is generated by the application itself (Phase 10 SITM features). Local analysis of the sitemap file provides real, useful health information without any API dependency. Admin can see at a glance if the sitemap is healthy.

### D-04: Page Layout — Single scrollable page

All 3 sections (overview, keywords/CTR, health) live on one page at `/admin/settings/seo/analytics` as a vertically scrollable layout. No tabs or sub-routes. Use ComponentCard wrappers for each section, consistent with other SEO sub-pages.

**Why:** The analytics page already exists as a single placeholder page. The 3 sections flow naturally as a dashboard — admin scrolls to see all data. Matches the pattern of other SEO settings pages (each is a single page). Simpler than tabs or sub-routes for what is essentially a dashboard view.

### D-05: Time Ranges — 7d, 30d, 90d, Year

Charts support 4 preset time ranges: 7 days, 30 days, 90 days, and 1 year. Uses the existing DateRangeSelector component pattern from the admin dashboard.

**Why:** Matches the admin dashboard's DateRangeSelector. 4 options cover short-term, monthly, quarterly, and yearly views. Consistent UX across the admin panel.

### D-06: Charts — ApexCharts with RevenueChart pattern

Use ApexCharts (already installed: apexcharts ^5.12.0, react-apexcharts ^2.1.0) following the RevenueChart.tsx pattern with dynamic import for SSR compatibility. Charts for: traffic overview trend, CTR/impressions (placeholder data), keyword position history (placeholder).

**Why:** ApexCharts is already in the project and working in RevenueChart. Dynamic import handles SSR. Reusing the established pattern ensures visual consistency with the admin BI dashboard.

## Codebase Context

### Reusable Assets
- **RevenueChart.tsx**: ApexCharts wrapper with dynamic import, bar/area types, date range support — direct template for analytics charts
- **DashboardKPIs.tsx**: Card-based KPI display with trend indicators (up/down/flat arrows) — template for analytics overview cards
- **DateRangeSelector.tsx**: 7d/30d/90d/year selector — reuse directly
- **getGa4Summary()**: Already fetches activeUsers, pageviews, sessions, topPages from GA4 API — extend for analytics overview
- **ComponentCard.tsx**: Standard section wrapper — use for each analytics section
- **Badge.tsx**: Status badges with variants — use for health indicators
- **CoreWebVitalsCards.tsx**: Placeholder card pattern with "--" values — follow for keyword/CTR placeholders
- **admin-dashboard.ts**: Server action pattern for KPI/chart data — follow for analytics actions

### Integration Points
- `src/app/(admin)/admin/settings/seo/analytics/page.tsx` — Replace placeholder with real dashboard
- `src/app/(admin)/actions/admin-tracking-v2.ts` — Extend getGa4Summary for analytics overview
- `src/lib/db/schema.ts` — Add seo_404_errors table
- `src/proxy.ts` — Add 404 logging when no route/redirect matches
- `src/app/(admin)/actions/admin-seo.ts` — Add sitemap health analysis, 404 report actions
- `src/lib/seo-keys.ts` — No new keys needed (analytics is read-only dashboard, not settings)

### Established Patterns
- **Server action**: requireAdmin() guard → DB query → return typed data
- **Client component**: `"use client"` + useState + useTransition + ComponentCard sections
- **Chart**: Dynamic ApexCharts import with SSR guard, configurable options
- **Card layout**: ComponentCard title/desc wrapper with internal grid/flex layout
- **Placeholder data**: "--" values with API connection note (Phase 12 CWV precedent)
